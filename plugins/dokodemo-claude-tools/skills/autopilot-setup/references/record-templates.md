# 記録ファイル・周辺ファイルの雛形

autopilot-setup スキルが生成する各ファイルの雛形。`{{...}}` を置換して使う。

## docs/tasks.md

```markdown
# タスクバックログ（tasks）

docs/autopilot.md の手順で運用する、タスク状態の単一の真実。タスクIDは T-001 からの連番（欠番可・再利用不可）。

書式:

​```
- [ ] T-xxx: <内容> ／ 受け入れ条件: <動いている実物の上で確認できる条件> [build] [ui]
​```

`[build]` マークが付いたタスクは検証ゲートにビルドを含める。
`[ui]` マークは見た目・触り心地（UI/UX）に影響するタスクに付ける（実装前に docs/direction.md 必読・完了時に評価リクエストの発行対象。詳細は docs/autopilot.md）。
受け入れ条件は必ず「実物で確認できる状態」を含めること（「ユニットテストが通る」だけは不可。純粋ロジックタスクは配線タスクとペアで起票する）。

DONE が12件を超える、またはこのファイルが 8,000字（`wc -m`）を超えたら、手順5（記録）の中で古い項目を docs/tasks-archive.md へ切り出す（専用のメンテナンスサイクルは作らない。詳細は docs/autopilot.md の手順M）。DONE の完了メモは **200字以内**（詳細はコミットメッセージと journal に書く）。

## DOING

（なし）

## TODO

- [ ] T-001: スモークスクリプトの整備 ／ 受け入れ条件: {{SMOKE_TASK_CRITERIA}}
- [ ] T-002: テスタビリティフックの実装 ／ 受け入れ条件: {{TESTABILITY_TASK_CRITERIA}}

## REVIEW（評価待ち）

（なし — 実装・検証・コミット済みで、評価リクエストへのユーザー応答を待っているタスク。応答が届いたら反映ターンが DONE か再着手へ動かす）

## BLOCKED

（なし）

## DONE

（なし）
```

セットアップ時に T-001/T-002（検証基盤）を必ず先頭に置く。セットアップ対話の中でスモークをその場で作成済みの場合、T-001 は最初から DONE に置いてよい。続けて垂直スライスに向けた最初の数タスクをユーザーと相談して起票する（無ければループ初回の手順Gに委ねてもよいが、垂直スライスの分解まではセットアップ時に済ませておくとループの立ち上がりが速い）。

## docs/journal.md

```markdown
# 作業ログ（journal）

追記専用。1サイクルにつき1エントリ、**1エントリ1,200字以内**に収める（行数ではなく文字数で守ること。1行に数百字を詰めれば行数の制約は無害に迂回できてしまう）。新しいエントリを上に追加する。

このファイルが 20,000字（`wc -m`）を超えたら、手順5（記録）の中で古いエントリを docs/journal-archive.md へ切り出す（専用のメンテナンスサイクルは作らない。詳細は docs/autopilot.md の手順M）。

書式:

​```
## <YYYY-MM-DD HH:MM> — <T-xxx タイトル ／ または「ゴール設定」「手順P」「メンテナンス」>
- やったこと:
- 詰まった点・気づき:
- 次サイクルへの申し送り:
​```

---
```

追記時の注意（insights.md 側にも初期知見として入れる）: 直前エントリの見出し行を巻き込んで消す事故が起きやすい。追記後に `grep -n "^## " docs/journal.md` で見出し数が+1になっているか確認する。

## docs/insights.md

```markdown
# 気づき・申し送り（insights）

次のイテレーションの自分が状態確認時に必ず読むファイル。ハマりどころとその回避策・採用した設計パターン・「やらない」と決めたこと等を書く。

journal.md（追記専用の履歴）と違い、ここは**常に「現在有効な知見」だけ**を保つ。古くなった項目は更新・削除してよい。12,000字（`wc -m`）を超えたら手順Mに従い統合・整理する（アーカイブせず、要約して簡潔に保つ）。

同じ種類のハマりを3回書くことになったら、ここに書き足すのをやめて **TODO タスクとして起票する**（3回踏むのは構造の問題であり、知見の共有では止まらない）。

## 設計パターン・規約

（まだなし）

## ハマりどころと回避策

- journal.md へ追記する際は、追記後に `grep -n "^## " docs/journal.md` で見出し数が追記前+1になっているか確認する（見出し巻き込み消去事故の防止）

## やらないと決めたこと

（まだなし）
```

## docs/direction.md（評価リクエスト運用を使う場合のみ生成）

goal（= ゴール文書。新規ファイルは作らず既存の {{GOAL_DOC}} を充てる）・direction・feedback-log の3点が、ユーザーと AI の共有状態になる。direction はユーザー評価の蒸留物であり、**本文の書き換えは承認済みの差分の反映（蒸留の配管）だけ**に限る。

```markdown
# 方向性（direction）

このプロジェクトにおける「良い」の判断基準の蒸留物。`[ui]` タスクの実装前と計画ターンに必ず読む。

更新ルール:
- **本文（基準・参照画像・やらない方向）を書き換えてよいのは、承認済みの差分提案を反映するときだけ**（蒸留ターンが差分を作り、評価リクエストでユーザー承認を得てから反映する。詳細は docs/autopilot.md の手順D・手順R）
- ユーザーも手編集しない。方向性の意図は対話・評価応答で伝え、蒸留ターンが差分化する
- 1項目1〜2行。根拠となった評価があれば feedback-log の F-xxx を添える

## レビュー関与度

ユーザーがどの細かさまで評価に関与したいかの現在値。評価リクエストの発行判断はこれを閾値として使う（詳細は docs/autopilot.md 手順5）。更新は本文と同じく蒸留の配管のみ（蒸留ターンが応答パターンを根拠に変更を提案する）。

- 現在値: **標準**
- 粗い: ゴール完了時のまとめ評価と方向性の分岐だけ発行する
- 標準: 上に加え、前例が無く判断が割れる見た目/UXの選択も発行する
- 細かい: 上に加え、細部（余白・色・文言など）でも基準と前例から自信を持って決められないものは発行してよい

## 基準

（まだなし。例: 「画面は密度重視。恒常表示の補助パネルより折りたたみを選ぶ（F-003）」）

## 参照画像

（良かったスクショ・目指す見本の URL と一言。消えない置き場の URL を使う）

## やらない方向

（まだなし）

## 承認待ちの差分提案

（なし — 蒸留ターンがここに提案を書いて評価リクエストを発行し、承認応答を受けたターンが本文へ反映して空に戻す）
```

## docs/feedback-log.md（評価リクエスト運用を使う場合のみ生成）

```markdown
# 評価ログ（feedback-log）

評価リクエストへのユーザー応答の生ログ。追記専用・direction への蒸留の原料。反映ターン（評価応答プロンプトを受けたターン）が追記する。新しいエントリを上に。

蒸留ターンで direction に昇格（または昇格不要と判断）したら、`[未蒸留]` を `[蒸留済 YYYY-MM-DD]` に書き換える。未蒸留件数は `grep -c "\[未蒸留\]" docs/feedback-log.md` で数えられる。

書式:

​```
## F-xxx <YYYY-MM-DD> [未蒸留] — 評価リクエスト #N「<狙い>」
- 問い:
- 応答: <選択肢> ／ <コメント>
- 対応: <起票したタスク T-xxx ／ 対応不要>
​```

---
```

## サイクルプロンプト（ユーザーがループで送る固定プロンプト）

セットアップ完了時にユーザーへ提示する。cron・dokodemo-claude の prompt_broadcast・/loop スキル等、送信手段は問わない。

**推奨（dokodemo-claude-tools プラグインが有効な環境）**: `autopilot` スキルを呼ぶだけでよい。

```
/dokodemo-claude-tools:autopilot
```

**フォールバック（プラグインが無い環境で回す場合）**:

```
docs/autopilot.md を読み、記載の手順に従って1サイクルだけ作業してください。手順書にないことはせず、サイクルが終わったら停止してください。
```

補足として案内すること:
- 1サイクルの所要は5〜20分程度。送信間隔は前サイクルの完了を待てる長さにする（Claude Code は処理中に届いたメッセージが割り込みになる場合があるため、キュー型の送信手段が望ましい）
- 初回の1〜2サイクルは人間が画面を見ながら回し（ドライラン）、手順の解釈ズレがないか確認してから無人化することを強く推奨
- 朝（ループ終了後）は autopilot-review スキルでふりかえりを行い、`docs/autopilot/shots/` のスクリーンショットと journal.md を確認する

## プロジェクトの CLAUDE.md への追記スニペット

既存の CLAUDE.md の運用ルール（コミット禁止・devサーバー起動禁止等）と autopilot.md が矛盾しないよう、以下の節を CLAUDE.md に追記する（既存の記述に合わせて調整）:

```markdown
### 自律運転モード（autopilot）
`docs/autopilot.md` に従う無人ループで作業する場合、本ファイルの運用ルールより autopilot.md の規定が優先する。具体的には:

- **Git**: `{{WORK_BRANCH}}` ブランチへの直接 `git commit` 可。ただし `git push`・リモート操作・デプロイ等の公開行為はいかなる場合も絶対禁止
- **開発サーバー**: 検証目的に限りバックグラウンドで起動してよい。サイクル終了前に必ずプロセスを停止する
- **ライブラリ調査**: context7 MCPが利用できない環境では、公式ドキュメント参照などの代替手段で調査して進めてよい
```
