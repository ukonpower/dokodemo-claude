# autopilot-distill

autopilot（無人開発ループ）の**蒸留ターンを1回だけ**実行する。評価リクエストへのユーザー応答の生ログ（docs/feedback-log.md）から「良し悪しの判断基準」を抽出し、方向性文書（docs/direction.md）への**差分提案**を作って、その承認をユーザーに評価リクエストとして仰ぐ。

direction はユーザーの判断基準の蒸留物であり、意図しない改変を防ぐため**差分提示 → ユーザーの承認**を必ず通す。このスキルは差分の提案と承認リクエストの発行までを担い、direction 本文の書き換えは承認応答が届いたターン（反映ターン）が行う。

## Critical（このターンの不変条件）

1. **direction.md の本文（基準・参照画像・やらない方向）をこのターンで書き換えない**。書いてよいのは「承認待ちの差分提案」節だけ
2. **実装しない**。変更してよいのは direction.md（提案節）と feedback-log.md のみ。ソースコード・tasks.md には触れない
3. **1回の実行で蒸留ターン1回のみ**。提案の発行後は応答を待たずに停止する
4. **公開行為・git の破壊的操作をしない**（push・リモート操作・reset --hard 等。autopilot 本体と同じ禁止事項に従う）
5. **自動起動しない**。ループのサイクルプロンプトや計画ターンから連鎖して呼ばない（計画ターンは未蒸留件数の報告と推奨までに留める）

## Instructions

### Step 1: 前提の確認

1. `docs/autopilot.md` を読む。**手順D（蒸留ターン）のセクションがあればそれに従う**（プロジェクト側の手順が優先。ただし上記の不変条件は破らない）
2. `docs/direction.md`・`docs/feedback-log.md` を読む。どちらかが存在しない場合は「評価リクエスト運用がセットアップされていない。autopilot-setup スキルで生成が必要」と報告して終了する
3. direction.md の「承認待ちの差分提案」節に前回の提案が残っていれば、新しい提案を重ねず「承認待ちの提案が残っている（受信箱の応答待ち）」と報告して終了する

### Step 2: 未蒸留エントリの分析

1. feedback-log.md の `[未蒸留]` エントリをすべて読む（0件なら「蒸留する原料がない」と報告して終了）
2. 基準に昇格させる候補を絞る:
   - **繰り返し現れている反応**（同種の指摘・同方向の選択が2回以上）を優先する
   - 1回きりの反応は無理に一般化しない（過度な一般化は基準を暴れさせる。次回の蒸留まで未蒸留のまま残してよい）
   - 個別の修正指示（「この画面のここを直す」）は基準ではなくタスクの領分。昇格させない
3. 既存の direction.md の基準と突き合わせ、「新規追加」「既存項目の強化・具体化」「既存項目と矛盾（要更新）」に分類する
4. **レビュー関与度の見直し**: direction.md の「レビュー関与度」も蒸留の対象。応答パターンに次の傾向があれば関与度の変更を提案に含める（これも差分提案→承認の配管を通す。勝手に書き換えない）:
   - 細かい粒度の発行への応答が「OK・コメント無し」ばかり続いている（同種2〜3回以上）→ 1段粗い側へ
   - まとめ評価・広域の発行への応答に、細部（余白・色・文言など）への具体的な修正コメントが繰り返し付く → 1段細かい側へ

### Step 3: 差分提案の作成

direction.md の「承認待ちの差分提案」節に、以下の形で提案を書く（**本文はまだ書き換えない**）:

```markdown
## 承認待ちの差分提案

<!-- 提案日: YYYY-MM-DD ／ 原料: F-xxx, F-xxx -->
- 追加: 「<基準の文（1〜2行）>」（F-xxx）
- 変更: 「<既存項目>」→「<新しい文>」（F-xxx）
- 削除: 「<陳腐化した項目>」
- 関与度: 標準 → 粗い（F-xxx, F-xxx: 細かい発行に OK のみの応答が続いたため）
```

- 1回の提案は**3項目程度まで**に絞る（多すぎると承認の判断コストが上がり、受信箱で返せなくなる）
- 各項目に原料となった F-xxx を添える（ユーザーが根拠を辿れるように）

### Step 4: 承認リクエストの発行と停止

1. 差分提案を評価リクエストとして発行する。発行手段は dokodemo-claude-tools の `review_request` MCP ツール（フル名 `mcp__plugin_dokodemo-claude-tools_api__review_request`。作法は dokodemo-review スキル参照）:
   - `aim`: 「direction の更新提案（未蒸留 N 件の蒸留）」
   - `question`: 提案の全文（追加・変更・削除の各項目）を含め、「この基準の更新を承認するか」を問う
   - `choices`: `["承認", "却下", "修正して再提案"]`
2. `review_request` が使えない環境では、提案内容を本文で提示し、ユーザーの承認をこの場の対話で得る（承認されたらその場で本文へ反映してよい。これは配管の代替であり、承認を経る原則は変わらない）
3. direction.md（提案節）の変更をコミットする（コミットの担い手が別にある運用なら autopilot.md 手順6に従い `git commit` しない）
4. 終了報告に以下を含めて停止する:
   - 未蒸留エントリ数と、提案に採った/見送った件数
   - 提案の要約（1行×項目数）
   - 「承認応答は受信箱から。応答が届いたターン（手順R）が本文への反映と `[蒸留済]` マークを行う」

### 承認応答が届いたら（このスキルの外・手順Rの領分）

応答はキュー経由の `[評価リクエスト #N への応答]` プロンプトとして届き、それを受けたターンが処理する（autopilot.md の手順R）: 承認なら提案を本文へ反映して提案節を空に戻し、原料の F-xxx を `[蒸留済 YYYY-MM-DD]` へ更新。却下なら提案を破棄して feedback-log にその旨を残す。修正なら コメントに従って提案を作り直し、再発行する。

## Examples

### Example 1: 未蒸留が溜まったのでユーザーが手動起動

User says: "蒸留して"

Actions:
1. autopilot.md の手順D・direction.md・feedback-log.md を読む
2. 未蒸留6件のうち「密度の高いレイアウトを好む」系の反応が3件 → 基準候補に。1回きりの色の指摘は見送り
3. 提案節に「追加: 画面は密度重視…（F-004, F-007, F-009）」を書き、review_request で 承認/却下/修正 の選択肢付きで発行
4. コミットして停止

Result: 「未蒸留6件中3件を1項目に蒸留して提案。承認は受信箱から」と報告

### Example 2: 計画ターンの報告を見て起動

Loop の計画ターンが「未蒸留7件。蒸留ターンの実行を推奨」と報告 → ユーザーが "/dokodemo-claude-tools:autopilot-distill" を送る

Actions: Example 1 と同じ手順を1回実行して停止する

## Troubleshooting

### 蒸留のたびに direction が大きく書き換わる

**Cause:** 1回きりの反応まで一般化している・1回の提案に項目を詰め込みすぎ
**Solution:** 繰り返し（2回以上）の反応だけを昇格させ、提案は3項目程度まで。見送った未蒸留は次回に持ち越す

### 提案が承認されないまま溜まる

**Cause:** 前回の提案が受信箱で未応答のまま新しい提案を重ねようとしている
**Solution:** Step 1-3 のとおり、承認待ちが残っている間は新しい蒸留をしない。受信箱の応答を待つ

### direction に基準を直接書き足してしまった

**Cause:** 反映ターンや実装ターンが「気づいたので」と本文を編集した
**Solution:** 差分提示→承認の配管を通っていない変更は取り消し、feedback-log 経由で蒸留に乗せ直す。direction 本文の変更は常に承認済み差分の反映だけにする
