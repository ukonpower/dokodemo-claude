# フィードバックループ設計 — 評価リクエストと方向性文書

ユーザー・Claude・dokodemo-claude の三者で「抽象的な目標からリリース品質へ収束させる」ためのフィードバックループの設計文書。実装委譲の起点となる仕様を定める。

## 1. 背景と問題の構造

- ループによる自動実装（autopilot 等）は、与えられたゴールに忠実にタスクを消化するが、**ゴール自体の誤りを検出・修正する機構がない**
- 「使いやすい触り心地」「いい感じの画面」といった抽象目標は事前に仕様として書き下せない。ユーザーの判断基準は暗黙的で、**具体物への反応（評価）としてしか出力されない**
- 唯一の正解信号であるユーザーの評価がループに入る経路が細い:
  1. 見るのに手間がかかる（動かす・環境を立てる）
  2. 言語化に手間がかかる
  3. 言語化しても揮発する（次サイクルの入力に戻らず、同じ指摘を繰り返すことになる）

### 三者の役割と 4 つの流れ

| アクター | 固有の能力 | 固有の制約 |
|---|---|---|
| ユーザー | 「良い」の判定基準を持つ唯一の存在 | 基準は暗黙的。具体物への反応としてしか出力できない。時間は細切れ |
| Claude | 生成・検証・雑務の大量実行 | セッション単位で記憶が切れる。テキストと構造化ファイルしか読めない |
| dokodemo-claude | 二者の間に常駐する媒体（保管と変換） | 自分では生成も評価もしない |

```
        ①意図 ──────────▶
 ユーザー                      Claude
        ◀────────── ②提示
        ③評価 ──────────▶
        ◀──── ④共有状態 ────▶   （両者が読み書きする置き場）
```

現状の dokodemo-claude は ①（キュー・ループ・broadcast・worktree 委譲）が厚く、②③④が未整備。本設計は ②③④ を埋める。

## 2. 共有状態の設計（④）

### 2.1 構成: 3 ファイル分離

寿命の違う 3 種類を別ファイルで持つ。**各プロジェクトのリポジトリ内 `docs/` に置く**（worktree・委譲先に自動で届く。ユーザーの評価基準はプロジェクトの性質によって切り替わるため、プロジェクト側配置とする）。

| ファイル | 中身 | 更新頻度 |
|---|---|---|
| goal | 何を作るか・完成の到達ライン | たまに変わる |
| direction | 良し悪しの判断基準の蒸留物（方向性） | 評価のたびに少しずつ育つ |
| feedback-log | 評価の生の反応の追記型ログ（蒸留の原料） | 応答のたびに追記 |

### 2.2 更新の担い手

- **feedback-log への追記と、direction への蒸留は Claude が行う**
- ユーザーは direction を読み、方向性の意図だけを対話で伝える（手編集はしない）
- direction の書き換えは**差分提示 → ユーザーの一言承認**を必ず通す（意図しない改変の防止）

### 2.3 読み分け（注入経路）

ループの手順に読み込みを組み込む。どれを読むかは AI のその場の判断に委ねず、**ターン種別に静的に紐付ける**。タスクには UI / logic の種別タグを付け、UI 系タスクなら direction 必読とする。

| ターンの種類 | goal | direction | feedback-log |
|---|---|---|---|
| 実装ターン（UI・見た目・UX を触る） | − | **必読** | 読まない |
| 実装ターン（内部ロジックのみ） | − | 読まない | 読まない |
| 計画ターン（autopilot-plan 等） | **必読** | 必読 | 読まない |
| 蒸留ターン（評価→基準への昇格） | − | 必読（更新対象） | **必読**（原料） |
| そもそも論の対話（ユーザーと） | 必読 | 必読 | 必要なら |

### 2.4 画像

direction には参照画像（良かったスクショ・目指す方向の見本）を URL で貼れるようにする。dokodemo-claude のアップロード機構を使うが、**基準文書から参照される画像は消えない置き場（恒久アップロード先と安定 URL）が必要**（現状の preview 機構は「その場で見せる」用途のため、実装時に手当てする）。

## 3. 評価リクエスト（②③の単位）

Claude がスクショを垂れ流すのではなく、「問い＋判断材料＋応答手段」を 1 セットにした**評価リクエスト**を dokodemo-claude の第一級オブジェクトとする。

### 3.1 中身

- **狙い**: このサイクルで何を改善しようとしたか（1〜2 行）
- **問い**: 何を判断してほしいか
- **提示物**: スクショ（複数案あれば並べる）、必要なら実機 URL。動画は後段スコープ
- **応答形式の指定**: 選択肢（A/B/採用しない 等）＋自由記述欄

提示側（Claude）が「どの応答形式で答えられる問いか」まで整形して出す。「どう思う？」の丸投げは評価コストを最大化するため禁止。

### 3.2 応答の 3 種（コスト順）

1. **選択**: A/B/どれも不採用
2. **一言**: 「B だけどヘッダーが安っぽい」のような添え書き
3. **そもそも**: 提示物レベルでなく方向がずれている場合。goal / direction を文脈に積んだ通常の対話を開始する（そもそも論の振り返りは「direction を挟んだチャット」として実現）

### 3.3 受信箱

dokodemo-claude の Web UI に評価待ち一覧（受信箱）を設ける。1 リクエストにつき「狙い → 提示物 → 応答ボタン」が縦に並び、スマホで 3 秒〜1 分で返せる形。ターミナル・キューと並ぶ恒常的な場所となる。

### 3.4 発行の粒度とレビュー関与度、ブロッキング発行

タスク粒度（1 サイクル = 1 タスク）のまま発行すると、レビュー粒度もタスク粒度に直結し、「余白はこれでよいか」級の追認が受信箱を埋める（実運用で確認済み。応答の大半が「OK・コメント無し」になる）。ここで問題だったのは「細部のレビューが混ざること」ではなく「情報量ゼロのレビュー（全部 OK で返るもの）が量産されたこと」。したがって発行の判定軸は解像度（細部か広域か）ではなく**「ユーザーの応答が成果物を実質的に変える見込みがあるか」**に置く。自明なものは広域でも発行せず、判断が割れるなら細部でも発行してよい（1 つのループに詳細と広域のレビューが混ざることは許容する）。

その閾値はプロジェクトごとに違う（見た目が商品そのものの一点物サイトでは細部までユーザーが見たいし、自分用ツールなら方向性だけでよい）。この閾値を**レビュー関与度**（粗い / 標準 / 細かい）として direction 文書に 1 項目で持たせる:

- **粗い**: ゴール（マイルストーン）完了時のまとめ評価と、方向性の分岐（進むと大きな手戻りになりうる選択）だけ
- **標準**（既定）: 上に加え、前例が無く判断が割れる見た目/UX の判断（複数案の選択）
- **細かい**: 上に加え、細部（余白・色・文言など）でも direction と前例から自信を持って決められないもの

関与度は静的な設定ではなく、**蒸留ターンが応答パターンから更新を提案する**（細かい発行に「OK・コメント無し」が続けば粗い側へ、まとめ評価に細部への修正コメントが繰り返し付けば細かい側へ）。手動の設定 UI にしないのは、フェーズが変わるたびの切り替え忘れが「追認で埋まる」問題を設定ミスとして再導入するため。どの関与度でも、direction と承認済みの前例から答えが出る判断は AI が自己判断する（前例の蓄積は蒸留ターンが担う）。

**ブロッキング発行（`blocking: true`）**: 後続の作業全体が評価結果に依存するときだけ使う例外形。発行と同時に発行元のキュー・ループが一時停止し、応答（または削除）で自動再開される。再開時、応答の反映ターンが次のループ周回より先に配達される。止まる理由と再開の契機が 1 機能で閉じているため、「止まりっぱなしに気づかない」事故が起きない。受信箱では「ループ停止中」バッジ付きで優先表示される。

## 4. 1 サイクルのフロー

```
[サイクルN]  実装 → 検証 → 評価リクエスト発行 → 記録・次タスクへ（ブロックしない）
                              │
[ユーザーの細切れ時間]  受信箱で開く → 選択/一言/そもそも を返す
                              │
[反映ターン]      AI の手が空き次第、応答が反映ターンとして届く → feedback-log 追記 → 修正タスク起票
                              │
[蒸留ターン]      ログが溜まったら direction の差分を提案 → ユーザーが一言承認
                              │
[サイクルN+k]  更新された direction を読んで実装 …（先頭に戻る）
```

### 段階 1: 発行（ループ実行中・Claude 側)

- UI タグ付きタスクの実装・検証ゲート通過後、「見た目・触り心地に影響する変更だったか」で発行を判定（手順書に 1 行ルールで記載。内部ロジックのみなら発行しない）
- **ループは評価を待たずに次のタスクへ進む**（応答は数時間〜半日単位で返るため、待つとループが止まる）
- tasks.md に「評価待ち」レーンを新設。**評価待ちの画面に依存する後続タスクだけ着手を保留**する

### 段階 2: 滞留と応答（ユーザー側)

受信箱で開き、選択 / 一言 / そもそも のいずれかを返す。

### 段階 3: 反映ターン（応答の還流)

**応答は「反映ターンの自動配達」で Claude に返す。** 応答の実体は `review-requests.json` に「回答済み・未反映」として永続化され、キューアイテムにはしない。キューは送信の手前で毎回「この宛先に未反映の応答が無いか」を確認し、あればキューアイテムより先に反映ターン（未反映ぶんを 1 プロンプトに束ねたもの）として配達、ターン完了時に反映済みマークを付ける。配達機会は「AI の手が空いた瞬間」すべて（応答直後・各ターンの Stop hook 着弾時・ループの周回間・キュー再開時）。配達内容は毎回永続データから組み立て直すため、**キューの削除・ループの停止再開で応答が失われることはない**。無人ループ中でも通常運用中でも同じ経路で動く。

このプロンプトを受けたターンがやること:

1. feedback-log に応答を追記（未蒸留マーク付き）
2. 具体的な修正指示なら tasks.md に修正タスクを起票。評価待ちレーンのタスクを DONE か再着手に移動
3. **direction はこのターンでは書き換えない**（蒸留ターンに委ねる）

### 段階 4: 蒸留ターン（direction の更新)

- **トリガー**: 未蒸留の feedback-log が一定件数（目安 5 件）溜まったら、計画ターンに併設して実行。応答 1 件ごとに即時蒸留しないのは、1 回の反応の過度な一般化で基準が暴れるのを防ぐため
- **承認フロー**: direction の変更差分を作り、**それ自体を評価リクエストとして受信箱に出す**（応答形式は 承認/却下/修正 の選択）。direction 更新も段階 1〜3 と同じ配管に乗せ、別の承認 UI を作らない
- 導入初期は自動トリガーにせず、ユーザーが「蒸留して」と指示する手動運用から始める

### 段階 5: 注入

承認された direction が 2.3 の読み分け表に従って以降のサイクルに読み込まれる。

## 5. 実装スコープ

### 新規に必要なもの

| もの | 種別 | 規模感 |
|---|---|---|
| 評価リクエストの発行 API＋保存 | backend | 中（preview_upload の拡張） |
| 受信箱 UI（一覧・応答） | frontend | 中 |
| 応答→反映ターンの自動配達 | backend | 小（キューの送信機構に相乗り） |
| 発行・反映・蒸留の手順 | スキル / 手順書テンプレ改訂 | 小 |
| goal / direction / feedback-log の雛形 | テンプレ | 小 |
| 画像の恒久置き場と安定 URL | backend | 小〜中 |

### 既存資産で賄えるもの

- 複数案生成: worktree 並列＋broadcast
- 応答の還流: キューの送信機構（反映ターンの自動配達）
- ループ実行: ループ・hooks
- スクショ撮影: agent-browser 等の既存スモーク機構

### 段階分け

1. **フェーズ 1**: 受信箱＋発行 API＋反映ターンの自動配達（段階 1〜3）。蒸留は手動運用
2. **フェーズ 2**: 蒸留の自動トリガー化、direction 差分承認の配管
3. **フェーズ 3**: 動画チャネル（触り心地の判断材料。唯一の新規インフラのため、フローが回ると確認できてから）
